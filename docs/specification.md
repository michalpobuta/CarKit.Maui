# CarKit.Maui — CarPlay + Android Auto library specification for .NET MAUI

Oct 29, 2026 · @Michał

## Goals and principles

CarKit.Maui is a NuGet library that gives .NET MAUI apps full Apple CarPlay and Android Auto support: all templates, all app categories, media, communication, and the map and turn-by-turn navigation, written 100% in C# on top of the official bindings.

**Project principles**

1. **A shared model where the platforms overlap; an escape hatch where they don't.** List, grid, tabs, alerts, information pane and search have a single model in C#. Features of one platform are available through types with a platform prefix (`CarPlay*`, `AndroidAuto*`) or through access to the native object.
2. **Imperative navigation stack.** The API mirrors the platforms: `SetRootAsync`, `PushAsync`, `PopAsync`, `PopToRootAsync`, `PresentAsync`, `DismissAsync`. Templates are not designed for continuous updates, so updates go through explicit `Update…` methods, with limit checks.
3. **Immutable model, per-platform renderer.** The model describes "what to show". The iOS renderer mutates `CP*` objects, the Android renderer rebuilds the template in `Screen.OnGetTemplate()` after `Invalidate()`.
4. **Zero manual configuration.** `Info.plist`, `AndroidManifest.xml`, entitlements and `automotive_app_desc.xml` are generated by MSBuild from a single section in the `.csproj`.
5. **Validation before the platform.** The library checks the category, allowed templates, stack depth and element limits before the CarPlay or Android Auto host throws an error at runtime.
6. **Integration with MAUI, not a dependency on the MAUI UI.** It works with DI and `MauiApp`, but does not render XAML in the car, except for the map surface.

**Out of scope (non-goals)**

- Android Automotive OS as a full platform with its own UI in Compose/Views. Only what the Car App Library and Media3 give "for free" on AAOS is supported.
- Custom map rendering. The library provides the surface and lifecycle, and the map is drawn by a map SDK or app code.
- Obtaining entitlements and store approvals. The library only documents the process.

**How to use this document in a coding session**

- Work through the stages from the "Stage plan" section in order. Each stage has acceptance criteria that must not be skipped.
- The type, namespace and project names in this document are binding. If they need to change, update the document first.
- Before implementing a template, check its row in the template catalog and the Apple/Google documentation given in the sources. Platform APIs change every year.
- Every public function requires a unit test on a fake host and a scenario in the sample app.

## Architecture

All screen logic lives in the immutable model in `CarKit.Maui.Core`, and two renderers translate it into native objects: on iOS by mutating `CP*` objects, on Android by rebuilding the template in `Screen.OnGetTemplate()`.

Domain modules depend on Core and have their own renderers in their packages. The app configures itself with a single `UseCarKit()` call, and the platform files are generated by `CarKit.Maui.Build`.

The POI, IoT, weather, voice and video templates are in the `CarKit.Maui` package, because they need no additional dependencies.

**Push vs pull model: reconciliation**

- Every model object (`CarTemplate`, `CarSection`, `CarListItem`, `CarAction`) has a stable `Id` (`Guid` by default, overridable).
- **iOS:** the renderer keeps an `Id → CP* object` map. `UpdateAsync` compares the old and new model and calls the cheapest native operation (`UpdateSections`, element properties, `UpdateGridButtons`), and only as a last resort swaps the template.
- **Android:** `CarKitScreen` holds the current model. `UpdateAsync` swaps the model and calls `Invalidate()`, and `OnGetTemplate()` builds the template from scratch. The renderer must preserve the same `Id` and template type so that the host does not count the refresh as a new task step.
- Refresh and step limits are platform-specific. The validator in Core knows them from a configuration table and throws `CarTemplateLimitException` with a description before the host rejects the template.

**Threads and lifecycle**

- The public API is asynchronous (`Task`). All native calls go through `ICarDispatcher` onto the main thread, and user callbacks (`OnSelected` etc.) are also invoked on the main thread.
- A car session can start without the phone UI: CarPlay connects the scene while the phone is locked, and Android starts `CarAppService` without an `Activity`. `IServiceProvider` must be available in both cases (MAUI creates `MauiApp` in the app delegate / `MauiApplication.OnCreate`). This is a mandatory test scenario.
- Disconnection destroys the renderer's state, but not the model's. Reconnecting invokes `OnConnected` anew, and the app can restore the stack from its own state.

**Images**

- Input: `CarImage` from a MAUI `ImageSource` (file, resource, stream, URI), a system symbol (SF Symbol / Material icon) or bytes.
- Output: `UIImage` with `UIImageAsset` (light and dark variants, the car screen scale from `CPTemplateApplicationScene.ContentStyle`) or `CarIcon` with `IconCompat` and an optional tint.
- Fetching from a URI is asynchronous, with an in-memory cache and a placeholder. Target sizes come from the per-template size table.
- Details (Stage 3): the placeholder is no image (Android Auto grid: the item's loading state), fetch and size limits and file sources — the "Template decisions (Stage 3)" table.

## Public API: core

The app implements a single `ICarAppHandler`, gets an `ICarSession` on connection, and builds screens from immutable C# records, which it updates with `with` expressions.

**Registration**

```csharp
builder
    .UseMauiApp<App>()
    .UseCarKit(car =>
    {
        car.Categories = CarAppCategory.Audio | CarAppCategory.Parking;   // defaults to <CarKitCategories> in the .csproj; a different value → startup error
        car.UseHandler<MyCarAppHandler>();                            // registered in DI as a singleton
        car.UseMedia(media => media.UseLibrary<MyMediaLibrary>());     // CarKit.Maui.Media
        car.UnsupportedTemplateBehavior = UnsupportedTemplateBehavior.UseFallbackOrThrow;
        car.Diagnostics.LogNativeCalls = true;                         // Debug only
        car.Android.AllowedHosts.Add("<sha256>,com.example.host");   // overrides the Release host list
    });
```

Categories are declared once, in the `.csproj` (`<CarKitCategories>`, the "iOS hosting" section). MSBuild generates the platform files from them and passes them to the runtime, so `car.Categories` is only for reading or confirmation.

**Contracts**

```csharp
public interface ICarAppHandler
{
    Task OnConnectedAsync(ICarSession session, CancellationToken ct);
    Task OnDisconnectedAsync(ICarSession session) => Task.CompletedTask;
}

public interface ICarSession
{
    CarPlatform Platform { get; }                 // CarPlay | AndroidAuto | AndroidAutomotive
    ICarCapabilities Capabilities { get; }        // iOS version, Car App API level, feature flags
    CarContentStyle ContentStyle { get; }         // Light | Dark
    IReadOnlyList<CarTemplate> Stack { get; }
    CarTemplate? Presented { get; }
    bool IsConnected { get; }

    Task SetRootAsync(CarTemplate root, bool animated = false);
    Task PushAsync(CarTemplate template, bool animated = true);
    Task PopAsync(bool animated = true);
    Task PopToAsync(CarTemplate template, bool animated = true);
    Task PopToRootAsync(bool animated = true);
    Task PresentAsync(CarModalTemplate modal, bool animated = true);   // alert, action sheet, voice
    Task DismissAsync(bool animated = true);
    Task UpdateAsync(CarTemplate updated);        // same Id, new content

    event EventHandler<CarTemplateEventArgs> TemplateAppeared;
    event EventHandler<CarTemplateEventArgs> TemplateDisappeared;
    event EventHandler<CarContentStyle> ContentStyleChanged;
    event EventHandler Disconnected;

    TNative? GetNative<TNative>() where TNative : class;  // CPInterfaceController / CarContext
}
```

**Model**

- All model types are `record`s with `init`: `CarTemplate` (abstract, `Id`, `Title`, `TabInfo`, `PlatformHooks`), `CarModalTemplate` (abstract), `CarSection`, `CarListItem`, `CarGridItem`, `CarAction`, `CarBarButton`, `CarImage`, `CarText` (text with variants for shortening).
- Collections are `CarArray<T>`: an immutable array (a wrapper over `ImmutableArray<T>`) with structural equality, collection expressions and implicit conversion from/to `ImmutableArray<T>`. `ImmutableArray<T>` itself compares references, so records would not have structural equality. Structural equality lets the renderer compute the differences.
- Handlers are `Func<CarItemContext, Task>`. On CarPlay the renderer keeps the item spinner until the `Task` completes and only then calls the completion handler. On Android, after completion it refreshes the screen if the model changed.
- Types shared by both platforms have no prefix (`CarListTemplate`). Single-platform types have a prefix (`CarPlayContactTemplate`, `AndroidAutoSignInTemplate`).

**Escape hatch**

```csharp
var list = new CarListTemplate("Stations") { Sections = [...] }
    .ConfigureCarPlay(cp => cp.EmptyViewTitleVariants = ["No stations"])   // CPListTemplate
    .ConfigureAndroidAuto(b => b.AddAction(mapButton))                        // ListTemplate.Builder (Car App API < 8)
    .ConfigureAndroidAutoSectioned(b => b.AddAction(mapButton));              // SectionedItemTemplate.Builder (API 8)
```

The `ConfigureCarPlay` and `ConfigureAndroidAuto` extensions live in the platform assemblies and store delegates in `PlatformHooks`. The renderer invokes them after building the native object (CarPlay) or right before the builder's `Build()` (Android Auto), on every render. Type list, order, thread and error handling: the "Platform template decisions (Stage 4)" table.

**Single-platform templates**

- `UnsupportedTemplateBehavior.Throw` – `CarTemplateNotSupportedException`.
- `UnsupportedTemplateBehavior.UseFallbackOrThrow` (default) – uses `template.WithFallback(otherTemplate)`, and throws an exception without a fallback.
- `ICarCapabilities.Supports<TTemplate>()` lets you check this earlier.

**Exceptions** (all inherit from `CarKitException`): `CarNotConnectedException`, `CarTemplateNotAllowedException` (template not allowed in the declared categories), `CarTemplateNotSupportedException`, `CarTemplateLimitException` (item count, stack depth, refresh limit), `CarStackException` (e.g. pushing the same template twice), `CarPlatformException` (wrapped native error).

**Usage example**

```csharp
public sealed class MyCarAppHandler(StationsService stations) : ICarAppHandler
{
    public async Task OnConnectedAsync(ICarSession session, CancellationToken ct)
    {
        var items = (await stations.GetNearbyAsync(ct)).Select(s => new CarListItem(s.Name)
        {
            Detail = s.Address,
            Image = CarImage.FromFile("station.png"),
            IsBrowsable = true,
            OnSelected = _ => session.PushAsync(new CarInformationTemplate(s.Name)
            {
                Items = [new("Free slots", s.FreeSlots.ToString())],
                Actions = [new CarAction("Navigate", _ => stations.NavigateAsync(s))]
            })
        });

        await session.SetRootAsync(new CarListTemplate("Nearby") { Sections = [new CarSection(items)] });
    }
}
```

**API decisions (Stage 1)**

| Topic | Decision |
| --- | --- |
| Namespaces | Core public API in `CarKit.Maui`; the Testing package in `CarKit.Maui.Testing` |
| Model hierarchy | `CarElement` (`string Id`, `Guid` in format `N` by default) → `CarTemplate` (`Title`, `TabInfo`, `LeadingBarButtons`, `TrailingBarButtons`, `PlatformHooks`, `Fallback`, `Kind`) → `CarModalTemplate`. Closed hierarchy (`private protected`). `PushAsync` with a modal → `CarStackException` |
| Platform SPI | `ICarHost`, `CarSession`, `CarTemplateValidator`, `CarCapabilities`, `CarPlatformRules` are internal; renderers, modules and Testing see them through `InternalsVisibleTo`. Host events (back, dismiss, theme, disconnect) are reported by the host through internal `CarSession` methods, passing the `Id` of the template that disappeared from the platform (not the stack position) |
| Images | `CarImage` with the variants `CarFileImage`, `CarUriImage`, `CarBytesImage`, `CarStreamImage`, `CarSymbolImage`, optional `Dark` and `Tint` (`CarColor`). Conversion from MAUI `ImageSource` in the `CarKit.Maui` package |
| `DismissAsync` | Without a presented modal it is a no-op |
| `UpdateAsync` | A template with the same `Id` in the stack or presented; type change → `CarStackException` |
| Limits | `car.Limits.OnOverflow` defaults to `Truncate`; `Throw` is a validation error that depends on `car.Validation` |
| Validation mode | Default taken from `AppContext` `CarKit.Maui.Validation` (`Strict`/`Warn`/`Off`); without an entry it is `Strict`. MSBuild (Stage 2) sets `Warn` in Release |
| Depth | Number of templates in the stack including the root; with multiple categories, the maximum. An overlay modal does not count; a modal that becomes a screen (`Message`) on Android after fallback consumes a step. AA task steps = depth, `UpdateAsync` does not consume a step |
| Built-in fallbacks | ActionSheet → Message, LongMessage → Information, VoiceControl → Message, Alert → Message; an explicit `WithFallback` takes precedence; `Id` preserved |
| Search | `OnSearchTextChanged: Func<CarSearchContext, Task<IReadOnlyList<CarListItem>>>`, `OnSearchSubmitted: Func<CarSearchContext, Task>` |
| Events | `TemplateAppeared`/`TemplateDisappeared` are emitted by the session after successful operations and after host pops |
| `CarPlayVideoBrowseTemplate` | Minimal model marked `[Experimental("CARKIT0001")]` until the iOS 27 API is verified; Stage 9: iOS 27 has no separate video template, so this is a video list (`CPListTemplate` with a details header, API 26.4), still experimental until tested with the iOS 27 SDK and a car with video. `CARKIT0001` also marks other iOS 27 models without a binding (`AllowsMiniPlayer`, `IsOverlay`) |
| `CarMessageTemplate` on CarPlay | Rendered as `CPInformationTemplate` (iOS 14+), because a screen on the stack cannot be a `CPAlertTemplate`; not available in the Audio category |
| `Id` uniqueness | Different elements with the same `Id` in one template are a validation error (the same instance in multiple places is allowed) |

## App categories and validation

The app declares categories with `CarAppCategory` flags. From them the library generates the entitlements and manifest and checks every template before sending it to the host.

**Category mapping**

| `CarAppCategory` | CarPlay | Android Auto | Module |
| --- | --- | --- | --- |
| `Audio` | audio | `MEDIA` via `MediaLibraryService` (media templates only in Early Access) | Media |
| `Communication` | communication | `MESSAGING` + `CALLING` (`CALLING` after the Core-Telecom binding, Stage 6) | Communication |
| `Navigation` | maps | `NAVIGATION` | Navigation |
| `Parking` | parking | `POI` | core |
| `EvCharging` | charging | `POI` | core |
| `Fueling` | fueling | `POI` | core |
| `QuickFoodOrdering` | quick-ordering | none | core |
| `DrivingTask` | driving-task | none | core |
| `VoiceConversational` | voice-based conversational (iOS 26.4+) | none | core |
| `Video` | video (iOS 27+, parked only) | none in Android Auto | core |
| `PublicSafety` | public safety | none | core |
| `Iot` | none | `IOT` | core |
| `Weather` | none | `WEATHER` | core |

**Validation implementation**

- The CarPlay and Android Auto matrices are data (`CarKit.Maui.Core/Rules/*.json` as an embedded resource), not code. Updating the rules requires no changes in the renderers.
- `CarTemplateValidator` checks: the template is allowed in any declared category, stack depth, `CarTabTemplate` children, element limits (from runtime, section above) and the minimum platform version.
- Android Auto: task step limit. Pushing a new template counts as a step, and refreshing the same template with the same `Id` does not. The validator counts the steps and throws `CarTemplateLimitException` before the limit is exceeded.
- Mode `car.Validation = Strict | Warn | Off`. `Strict` by default in Debug, `Warn` in Release (log + attempt to send).

## Domain modules

The Media, Communication and Navigation modules are separate packages, because on each platform they use different frameworks than the templates. The remaining categories are ready-made patterns on the main-package templates.

### Media (`CarKit.Maui.Media`)

The app implements two interfaces, and the module renders the library and Now Playing on both platforms.

```csharp
public interface ICarMediaLibrary
{
    Task<CarMediaItem> GetRootAsync(CancellationToken ct);
    Task<IReadOnlyList<CarMediaItem>> GetChildrenAsync(string parentId, int page, int pageSize, CancellationToken ct);
    Task<IReadOnlyList<CarMediaItem>> SearchAsync(string query, CancellationToken ct);
    Task<CarMediaItem?> GetItemAsync(string id, CancellationToken ct);
}

public interface ICarMediaPlayer   // adapter for the app's player
{
    IObservable<CarPlaybackState> State { get; }
    Task PlayAsync(string itemId); Task PauseAsync(); Task ResumeAsync();
    Task SeekAsync(TimeSpan position); Task SkipNextAsync(); Task SkipPreviousAsync();
    Task SetShuffleAsync(bool on); Task SetRepeatAsync(CarRepeatMode mode); Task SetRateAsync(float rate);
    Task InvokeCustomActionAsync(string actionId);
}
```

- `CarMediaItem`: `Id`, `Title`, `Subtitle`, `Artwork`, `IsPlayable`, `IsBrowsable`, `ChildrenStyle` (list/grid), `Duration`, `IsExplicit`, `Progress`, `IsPlaying`.
- **iOS:** automatic library browsing as a `CPTabBarTemplate` → `CPListTemplate` tree (option `media.UseAutoBrowse()`; screens can also be built by hand). Now Playing through `MPNowPlayingInfoCenter` and `MPRemoteCommandCenter`, `CPNowPlaying*Button` buttons, "Up Next", "Album/Artist". Sports mode (iOS 18.4, `CarNowPlayingTemplate.Sports`) and a MiniPlayer that can be disabled (iOS 27, `AllowsMiniPlayer` — blocked without Xcode 27; Stage 9). `AVAudioSession` in the `Playback` category.
- **Android:** `CarKitMediaLibraryService : MediaLibraryService` (Media3) translates `ICarMediaLibrary` into a `MediaItem` tree with content-style extras (list/grid), search and pagination. `CarKitPlayer : SimpleBasePlayer` adapts `ICarMediaPlayer` to `MediaSession`. The UI is drawn by Android Auto. `MediaPlaybackTemplate` (API 8) behind the `media.UseTemplatedMediaOnAndroid` flag – media templates are in Early Access.
- Audio focus, interruptions and ducking are handled by the module on both platforms.

### Communication (`CarKit.Maui.Communication`)

- **Conversations in a list:** `CarConversationItem` → `CPMessageListItem` (iOS) / `ConversationItem` (Car App Library 1.7). Actions: read aloud, reply, mark as read.
- **Message notifications:** `ICarMessageNotifier.NotifyAsync(conversation, message)` → on Android a `MessagingStyle` notification with semantic actions Reply / Mark as read (required by Android Auto); on iOS a notification category with `AllowInCarPlay` and authorization with the `CarPlay` option.
- **Sending and dictation:** iOS through SiriKit (`INSendMessageIntent`, `INSearchForMessagesIntent`) – requires an Intents Extension, which the sample must show in the .NET project; Android through `RemoteInput` in the Reply action.
- **Calls:** iOS through CallKit (`CXProvider`) + `CPContactTemplate` with call/message/directions buttons; Android through Jetpack Core-Telecom + the `CALLING` category.
- Details, type names and the Android calls gate (no Core-Telecom binding): the "Communication module decisions (Stage 6)" table.

### Navigation (`CarKit.Maui.Navigation`)

The largest module: map surface, navigation session, maneuvers, estimates, alerts, panning and the second screen.

```csharp
public interface ICarNavigationSession
{
    Task ShowTripPreviewsAsync(IReadOnlyList<CarTrip> trips, CarTrip? selected);
    Task StartTripAsync(CarTrip trip, CarRouteChoice route);
    Task UpdateManeuversAsync(IReadOnlyList<CarManeuver> upcoming);       // icon, instructions, lanes, distance
    Task UpdateEstimatesAsync(CarTravelEstimates trip, CarTravelEstimates? maneuver);
    Task ShowAlertAsync(CarNavigationAlert alert);
    Task RerouteAsync(CarRouteChoice route);                             // CPRouteInformation (iOS 17.4)
    Task PauseAsync(CarNavigationPauseReason reason);
    Task FinishAsync(); Task CancelAsync();
}
```

- **Map surface** `ICarMapSurface` with rendering variants:
  1. **Native map view:** iOS – `UIViewController` in `CPWindow` (MapKit, Mapbox, Google); Android – `VirtualDisplay` + `Presentation` on a `Surface` with `SurfaceCallback`, in which the native `MapView` runs.
  2. **Custom drawing:** `ICarSurfaceRenderer.Draw(ICanvas, RectF visibleArea, RectF stableArea)` on `Microsoft.Maui.Graphics`, the same code on both platforms.
  3. **MAUI view (experimental):** `View.ToPlatform(mauiContext)` in `CPWindow` / `Presentation`. No performance guarantees.
- **Interactions:** map buttons, pan (`CPMapTemplate` panning, `SurfaceCallback.OnScroll`), zoom (`OnScale`), fling, the visible and stable area passed to the renderer.
- **Route preview:** `CPMapTemplate.ShowTripPreviews` ↔ `MapWithContentTemplate` with a route list.
- **Second screen:** CarPlay Dashboard (`CPTemplateApplicationDashboardScene`, iOS 13.4) and instrument cluster (`CPTemplateApplicationInstrumentClusterScene`, iOS 15.4) as additional `ICarMapSurface` instances; navigation metadata for the cluster (iOS 17.4). Android: cluster via the `FEATURE_CLUSTER` category – verify support in Android Auto vs AAOS.
- **Voice prompts:** `ICarVoicePrompts` on `AVSpeechSynthesizer` with ducking (iOS) and TTS with transient audio focus (Android). Voice in CarPlay for navigation: `CPVoiceControlTemplate`.
- **Route sharing** (iOS 26.4+, car-dependent): optional (`nav.ShareRoutesWithCar`), `CarRouteSegment` segments and car requests in `ICarNavigationHandler`; test on a real device (see Risks) — "New platform features decisions (Stage 9)".
- Details, new types and decisions: the "Navigation module decisions (Stage 8)" table.

## iOS hosting

On iOS the library adds CarPlay scenes alongside the MAUI phone scene. MSBuild injects the configuration through .NET for iOS mechanisms (`PartialAppManifest`, `CustomEntitlements`), so the app does not edit `Info.plist` by hand.

**Configuration in the app's `.csproj`**

```xml
<PropertyGroup>
  <CarKitCategories>Audio;Parking</CarKitCategories>
  <CarKitIosPhoneSceneDelegate>SceneDelegate</CarKitIosPhoneSceneDelegate>  <!-- empty = library default -->
  <CarKitIosDashboard>false</CarKitIosDashboard>                            <!-- true only for Navigation with the module (CARKIT009) -->
  <CarKitIosInstrumentCluster>false</CarKitIosInstrumentCluster>            <!-- iOS 15.4; Android: CarKitAndroidCluster -->
</PropertyGroup>
```

**Generated scene manifest** (`PartialAppManifest` fragment)

| Scene role | Delegate | When |
| --- | --- | --- |
| `UIWindowSceneSessionRoleApplication` | the app's `SceneDelegate : MauiUISceneDelegate` or `CarKitPhoneSceneDelegate` from the library | always; configuration `__MAUI_DEFAULT_SCENE_CONFIGURATION__` |
| `CPTemplateApplicationSceneSessionRoleApplication` | `CarKitSceneDelegate` | always; the same configuration name, because `MauiUIApplicationDelegate.GetConfiguration` returns it for every role |
| `CPTemplateApplicationDashboardSceneSessionRoleApplication` | `CarKitDashboardSceneDelegate` | `CarKitIosDashboard=true` (with `CPSupportsDashboardNavigationScene`; Stage 8) |
| `CPTemplateApplicationInstrumentClusterSceneSessionRoleApplication` | `CarKitInstrumentClusterSceneDelegate` | `CarKitIosInstrumentCluster=true` (iOS 15.4, with `CPSupportsInstrumentClusterNavigationScene`; Stage 8) |

Additionally `UIApplicationSupportsMultipleScenes = true`, and for every declared category a `CustomEntitlements` entry with the corresponding `com.apple.developer.carplay-*` key.

**`CarKitSceneDelegate`**

- Inherits from `CPTemplateApplicationSceneDelegate`, marked `[Register("CarKitSceneDelegate")]`.
- Implements both `DidConnect` variants: without a window (templates) and with a `CPWindow` (navigation, the window goes to `ICarMapSurface`). Likewise both `DidDisconnect` variants.
- On connect: obtains `IServiceProvider` from `IPlatformApplication.Current`, creates the shared `CarSession` with the internal `CarPlayHost` (an `ICarHost` implementation on `CPInterfaceController`), sets `CPInterfaceControllerDelegate` (appear/disappear events) and calls `ICarAppHandler.OnConnectedAsync`.
- `ContentStyleDidChange` → `ICarSession.ContentStyleChanged` and regeneration of images with variants.
- Background navigation: `DidSelectManeuver` and `DidSelectNavigationAlert` are forwarded to the Navigation module.

**Critical requirements**

- CarPlay start with the phone locked, without a phone scene: `IPlatformApplication.Current` must exist. If MAUI creates `MauiApp` only at the phone scene, the library must force its creation in the app delegate. Mandatory test.
- Enabling the scene manifest changes the phone app's lifecycle (the `Window` and `Application` events in MAUI). The sample must confirm that `OnSleep`/`OnResume` and deep links still work.
  - Confirmed in Stage 2 (iOS 26 simulator): `OnSleep`/`OnResume` work. With the scene manifest, URLs go to `scene:openURLContexts:`, that is, to the MAUI lifecycle event `iOSLifecycle.SceneOpenUrl`, not `iOSLifecycle.OpenUrl`; an app that handles only `OpenUrl` must add `SceneOpenUrl` (the sample handles both). MAUI on iOS does not call `Application.OnAppLinkRequestReceived` at all, regardless of CarKit.
- In the CarPlay Simulator the entitlement must be in the build (Apple: "Simulator can't display your CarPlay-enabled app unless it has the necessary entitlements"), but it needs no Apple approval or profile: CarKit adds the category key to simulator builds (Stage 10, a fix to the Stage 2 decision). On a device and in TestFlight the entitlement must be granted by Apple. The provisioning profile with the CarPlay entitlement is generated in the Apple portal after the category is approved.

## Android hosting

On Android the library provides the base classes `CarAppService`, `Session` and `Screen`, and a source generator creates in the app's assembly a service class with `[Service]` and `[IntentFilter]` attributes matching the declared categories.

**Components**

| Class | Based on | Role |
| --- | --- | --- |
| `CarKitAppServiceBase` | `CarAppService` | `CreateHostValidator()` and `OnCreateSession()`; in the app, a generated subclass `CarKitGeneratedAppService` |
| `CarKitSession` | `Session` | `OnCreateScreen(Intent)`, `OnNewIntent` (navigation intents), lifecycle observer → `OnConnectedAsync` / `OnDisconnectedAsync` |
| `CarKitScreen` | `Screen` | Holds the current model; `OnGetTemplate()` calls the renderer; `UpdateAsync` → `Invalidate()` |
| `CarKitMediaLibraryService` | Media3 `MediaLibraryService` | Only for the `Audio` category, separate registration |
| `CarKitSurfaceCallback` | `SurfaceCallback` | Only the Navigation module and POI with a map (internal to the module; Stage 8) |

**Stack mapping**

- `SetRootAsync` → `ScreenManager.PopToRoot()` + swapping the root screen's model; with a different root template type and screens above it — a new root screen (Stage 3, "Template decisions (Stage 3)").
- `PushAsync` / `PopAsync` / `PopToAsync` → `ScreenManager.Push` / `Pop` / `PopTo(marker)`; marker = template `Id`.
- `PresentAsync(CarAlertTemplate)` → `AppManager.ShowAlert` (API 5), otherwise a `MessageTemplate` screen on the stack (modal screen: an action closes it, it consumes a task step).
- The host's Back button pops the screen; the library synchronizes `ICarSession.Stack` and emits `TemplateDisappeared`.

**Generated manifest entries and resources**

- A service with the intent filter `androidx.car.app.CarAppService` and categories `androidx.car.app.category.*`.
- `[assembly: MetaData("com.google.android.gms.car.application", Resource = "@xml/automotive_app_desc")]` and `androidx.car.app.minCarApiLevel` (from the `CarKitAndroidMinCarApiLevel` property, default 1).
- `automotive_app_desc.xml` generated by MSBuild as an `AndroidResource`: `<uses name="template"/>` for templates, `<uses name="media"/>` for Audio, `<uses name="notification"/>` for Communication with the module (messages from notifications, Stage 6).
- For Communication with the module: a notification action receiver (generated subclass `CarKitGeneratedMessageReceiver`, `exported=false`) and the `POST_NOTIFICATIONS` permission (Stage 6).
- `[assembly: UsesPermission(...)]` permissions depending on the category (Platforms section).
- For Audio: registration of `CarKitMediaLibraryService` with the filters `androidx.media3.session.MediaLibraryService` and `android.media.browse.MediaBrowserService` (generated subclass `CarKitGeneratedMediaLibraryService`, `foregroundServiceType="mediaPlayback"`, permissions `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_MEDIA_PLAYBACK`); an app with `Audio` only has no `CarAppService`.

**Host validator**

- Debug: all hosts allowed so that the DHU works.
- Release: the list of allowed hosts (Android Auto, AAOS template host) is shipped by the library as a resource; the app can override it via `car.Android.AllowedHosts`.

**Android Automotive OS**

- Disabled by default. `CarKitEnableAutomotive=true` adds the `Car.App.Automotive` package, `CarAppActivity` and `uses-feature android.hardware.type.automotive` with `required=false`.
- The `Car.App.Automotive` package has no .NET binding (as of 2026-10-29), so `CarKitEnableAutomotive` waits for a Microsoft binding.
- We support only what works on AAOS from the same template and Media3 code. A standalone UI on AAOS is out of scope.

**Template decisions (Stage 3)**

| Topic | Decision |
| --- | --- |
| CarPlay updates | `UpdateAsync` mutates the `CP*` objects in place: a list with the same structure (sections, headers, `Id`s and row types) through the `CPListItem` setters, a different structure through `UpdateSections`; a grid through `UpdateGridButtons`/`UpdateTitle`, a pane through `Title`/`Items`/`Actions`, tabs through `UpdateTemplates` (children with the same `Id` and type are updated recursively), search and handlers by replacing the model in the renderer state. A template is replaced only where CarPlay has no API: list title, pane `Layout`, alert and action sheet content. Template on top of the stack: pop+push without animation (for the root, only `SetRootTemplate`), modal: dismiss+present; deeper in the stack a title/layout change is skipped with a warning, and the rest is updated in place |
| Android Auto refreshes | `UpdateAsync` rebuilds the template of the same `CarKitScreen` (`Invalidate()`), and the choice of `ListTemplate`/`SectionedItemTemplate` is fixed per connection, so the host gets the same type. The CarKit host classifies every rebuild with the Car App Library rules (list: the previous one is loading, or the same title, sections, headers, row count and row titles; grid and pane analogously; message: title and text; search: every change; tabs: the same structure, and with the same active tab, its content). A refresh does not consume a step; a rebuild that is not a refresh consumes a screen step. `LongMessageTemplate` and `SignInTemplate` do not count toward the limit (javadoc: "does not count against the template quota"; Stage 4 fix). The step counter (host limit 5, the fifth template must finish the task: `PaneTemplate`, `MessageTemplate`, `LongMessageTemplate`, `SignInTemplate`; going back returns the screen's steps) reports exceeding it according to `car.Validation` (`CarTemplateLimitException` in `Strict`). The loading screen before the first `SetRootAsync` has the connection's list type (`ListTemplate` or `SectionedItemTemplate`), so a list root is a refresh |
| `SetRootAsync` on Android Auto | The same template type as the current root: `PopToRoot` and a rebuild of the root. A different type (also when there are no screens above, because a pop right before `SetRootAsync` leaves a pending return on the root): a new root screen (push, then `ScreenManager.Remove` of the old screens), because the host treats returning to a screen with a different template type as an error; the step counter then counts from 1 |
| Alert and action sheet | Selecting an action closes the modal on both platforms. Order: native dismissal, report to the session (`Presented == null`, `TemplateDisappeared`), and only then the action handler, which can immediately show another modal; `DismissAsync` in the handler is a no-op. Android Auto also closes the alert after `Duration` (default 10 s); CarPlay does not close the alert by itself. `FakeCarHost.SelectAsync` reproduces this order. The Android Auto modal screen (`Message` fallback) stays on top on `PopAsync`/`PopToAsync`/`PopToRootAsync`/`SetRootAsync` with the same root type (the screens under it are removed, as under a CarPlay modal); `PushAsync` and a new root screen close it, and the session learns about this synchronously (`CarSession.OnHostClosedModalDuringOperation`) |
| `SectionedItemTemplate` | From Car App API 8, if the `AppContext` switch `CarKit.Maui.Android.SectionedItemTemplate` is not set to `false`: section → `RowSection` (title = header), `CarListImageRowItem` → `GridSection`. Below API 8 or with the switch set to `false`: `ListTemplate`, and `CarListImageRowItem` → `Row` with the first image (choosing a single image is unavailable) |
| Images | File: app resource (`MauiImage`: on Android a drawable named after the file in the MAUI convention, on iOS a file in the bundle, also `.png` for `.svg`), then an absolute path, then `MauiAsset`. Symbol: SF Symbol; on Android an app drawable named `AndroidIconName` (the app adds the Material icon; `android.R.drawable` is not supported, because the public `IconCompat` stores the app package). File, resource, symbol and bytes are loaded immediately; URI (`http`, `https`, `file`) and stream asynchronously off the main thread, max. 5 MB and 20 s. LRU cache (64 entries) per connection. Until loaded: no image (Android Auto grid: the item's loading state, without an `OnClickListener`, which `GridItem` rejects while loading), then an in-place update (iOS: an item that is still waiting for the same image, also after in-place updates) or a screen refresh (Android). Error: no image and a `Warning` log, never an exception |
| Image variants and sizes | `Dark`: iOS `UIImageAsset` with both variants and re-setting the images after `ContentStyleDidChange`; Android chooses by `CarContext.IsDarkMode` and rebuilds the screens after a theme change (refresh). `Tint`: `CarIcon` (Android), `ApplyTintColor` (iOS). Size: iOS from the template's `MaximumImageSize` × the car screen scale; Android bitmaps max. 128 px (row, tab, action, alert) and 160 px (grid, message), because a template with bitmaps goes through the Binder |
| MAUI `ImageSource` | `CarImageSourceExtensions.ToCarImage(this ImageSource source)` in `CarKit.Maui`: `FileImageSource` → `CarImage.FromFile`, `UriImageSource` → `FromUri`, `StreamImageSource` → `FromStream`; other sources (e.g. `FontImageSource`) → `NotSupportedException` |
| Runtime limits | CarPlay: `ListItems` = `CPListTemplate.MaximumItemCount`, `ListSections` = `MaximumSectionCount`, `GridItems` = `CPGridTemplate.MaximumItems`, `Tabs` = `CPTabBarTemplate.MaximumTabCount`, `Actions` = `CPAlertTemplate.MaximumActionCount` (alert only; Stage 10). Android Auto (Car App API ≥ 2): `ConstraintManager.GetContentLimit` — list → `ListItems`, grid → `GridItems`, pane → `InformationItems`, place list → `PointsOfInterest` (route list: Stage 8). Read once per connection; an error or a value ≤ 0 → the default from the rules. The number of images in `CPListImageRowItem` is truncated to `MaximumNumberOfGridImages` |

| Unit (Core) | xUnit + `FakeCarHost` from `CarKit.Maui.Testing` | Stack, validator, limits, model diff, exception handling, threading through a fake dispatcher |
| iOS renderers | Device tests on the iOS simulator (`tests/CarKit.Maui.DeviceTests`, custom runner; XHarness not installed) | Model → `CP*` objects (they can be created without a car connection), updates, images |
| Android renderers | Device tests on the emulator (`tests/CarKit.Maui.DeviceTests`); `TestCarContext` if a binding for `androidx.car.app:app-testing` appears (as of 2026-10-29: not on NuGet) | Model → Car App Library templates, shape of refreshes, images; `Invalidate` and `ConstraintManager` require a host (logic tested on `net10.0`, run in DHU) |
| Scenarios | Sample + CarPlay Simulator (Xcode → I/O → External Displays → CarPlay) and DHU | Full flows per category, dark theme, resolutions, dashboard and cluster |
| Device | iPhone with a CarPlay profile + a car or a radio with CarPlay; a phone with Android Auto + a car or a radio | Navigation, audio, Bluetooth, start with the phone locked |

## Stage plan

Full support is 11 stages and roughly 25–32 weeks of work for one person full time; stage 8 (navigation) is the longest and riskiest. Carry out the stages in order, because each builds on the previous ones, and a stage is not finished until its acceptance criteria are met.

1. **Stage 0 – Repo skeleton** (approx. 0.5 wk)
   - Scope: solution, projects from the Architecture section, `Directory.Build.props` (nullable, analyzers, warnings as errors), CI, empty sample.
   - Acceptance: `dotnet build` passes for all TFMs on macOS; CI green; the empty sample starts on the iOS simulator and the Android emulator.
2. **Stage 1 – Core** (approx. 2 wk)
   - Scope: model of all 16 templates, elements and actions; `ICarSession` on `FakeCarHost`; validator with rules in JSON; exceptions; dispatcher.
   - Acceptance: Core test coverage ≥ 90%; tests of the stack, limits and category rules; public API reviewed and frozen in `PublicAPI.Shipped.txt`.
3. **Stage 2 – Hosting and build** (approx. 2 wk)
   - Scope: `CarKitSceneDelegate`, `CarKitPhoneSceneDelegate`, Android base classes, service source generator, MSBuild targets (`PartialAppManifest`, `CustomEntitlements`, `automotive_app_desc.xml`, permissions), `UseCarKit()` integration.
   - Acceptance: the sample shows `CarListTemplate` in CarPlay Simulator and DHU without manual editing of `Info.plist` or the manifest; the test of starting without the phone UI passes; the `CARKIT001` warning works.
4. **Stage 3 – Common templates** (approx. 3–4 wk)
   - Scope: List (including `SectionedItemTemplate` for API ≥ 8), Grid, Tab, Information, Search, Alert, Message, Action sheet, Long message; updates; image pipeline; limits from the runtime.
   - Acceptance: every template has a screen in the sample on both platforms and renderer tests; a list update on iOS does not replace the template; on Android a refresh does not consume a task step.
5. **Stage 4 – Platform templates and escape hatch** (approx. 1 wk)
   - Scope: `CarPlayContactTemplate`, `AndroidAutoSignInTemplate`, `CarVoiceControlTemplate`, `ConfigureCarPlay` / `ConfigureAndroidAuto`, fallbacks.
   - Acceptance: a test of each `UnsupportedTemplateBehavior` behavior; an escape hatch example in the sample.
6. **Stage 5 – Media** (approx. 3–4 wk)
   - Scope: the whole Media module on both platforms.
   - Acceptance: a player in the sample with a library of ≥ 3 levels, search, shuffle/repeat/playback rate; Android Auto shows the library through Media3; interruption by a call and playback resuming work on both.
7. **Stage 6 – Communication** (approx. 2–3 wk)
   - Scope: conversations in a list, `MessagingStyle` notifications with a reply, SiriKit Intents Extension in the sample, CallKit and Core-Telecom.
   - Acceptance: an incoming message read and replied to by voice in DHU; a contact with buttons in CarPlay Simulator; a VoIP call visible in the car.
8. **Stage 7 – POI and other categories** (approx. 2 wk)
   - Scope: POI on both platforms (with and without a map), quick ordering, IoT, weather, driver task, conversational apps.
   - Acceptance: the flow of each category in the sample; the validator rejects a template outside the category.
9. **Stage 8 – Navigation** (approx. 6–8 wk)
   - Scope: `ICarMapSurface` in three modes, navigation session, maneuvers, lanes, estimates, alerts, route preview, pan and zoom, dashboard, instrument cluster, voice prompts.
   - Acceptance: a simulated route goes from preview to end in CarPlay Simulator and DHU; a test on a real car or radio; map rendering smoothness measured in the diagnostic log, described in the PR.
10. **Stage 9 – New platform features** (approx. 1–2 wk)
    - Scope: video and MiniPlayer from iOS 27, Voice Control presentation style from iOS 27, Car App Library 1.8+ features when the binding is available.
    - Acceptance: features behind a version check; the sample shows them on supported versions, and on older ones the fallback works.
    - Result (2026-11-04): iOS libraries with `net10.0-ios` (26.0) and `net10.0-ios26.4` assets; `CarFeature` gate + `ICarCapabilities.Supports`; iOS 26.4: voice action buttons and modal bar, list header, item playback state, route waypoints, segments, detour reason and route sharing; iOS 18.4: typed sport mode; iOS 27 video as a list (API 26.4, experimental). Blocked: iOS 27 API (MiniPlayer, Voice Control overlay and the rest of the Xcode 27 b1 diff) — no Xcode 27; Car App Library 1.8+ — no .NET binding. Details: "New platform features decisions (Stage 9)".
11. **Stage 10 – Documentation and first public release** (approx. 1–2 wk)
    - Scope: documentation site, README, "first app in 15 minutes" quickstart guide, description of the entitlement and approval process, NuGet packages with symbols and Source Link.
    - Acceptance: all mandatory scenarios ticked on devices; `PublicAPI.Shipped.txt` updated; tag `v1.0.0`, preceded by public `v0.1.0-beta.N` tags.
    - Result (2026-11-04): documentation site `docs/site` (DocFX 2.81.0, 0 warnings, API reference for Core, Testing, the `net10.0-ios26.4` asset and Android-only types), quickstart guide verified by `eng/quickstart/run.sh`, entitlement and approval process, 0.1.0-dev packages with `.snupkg`, Source Link, READMEs and English descriptions, release rules (`CARKITREL001`–`003`), `eng/ReleaseGate` gate, `release.yml`, `docs.yml`, `CHANGELOG.md`, `CONTRIBUTING.md`, checklist with the owner's steps. Acceptance: met for `PublicAPI.Shipped.txt` (all `Unshipped` = `#nullable enable`). Not met: mandatory scenarios on devices (no DHU, car or signed builds; in the CarPlay Simulator window only the quickstart guide was run) and the release tags (repo without commits; the repo address is the owner's decision). The first opening of the CarPlay window revealed two defects in Stages 2–3, both fixed: CarKit apps did not show up in CarPlay Simulator, and the Audio app lost the primary alert action. Details: "Documentation and release decisions (Stage 10)", `docs/release-checklist.md`.

## Repository structure, conventions and risks

Platform code lives exclusively in `Platforms/`, Core does not know MAUI, and the entire library must be compatible with trimming and Native AOT, because iOS builds in AOT mode.

```text
CarKit.Maui/
├─ LICENSE, README.md, CHANGELOG.md, CONTRIBUTING.md, SECURITY.md, CODE_OF_CONDUCT.md
├─ src/
│  ├─ icon.png                     package icon
│  ├─ CarKit.Maui.Core/            Model/, Session/, Validation/, Rules/*.json, Abstractions/
│  ├─ CarKit.Maui/                 Hosting/, Platforms/iOS/, Platforms/Android/, buildTransitive/
│  ├─ CarKit.Maui.SourceGenerators/
│  ├─ CarKit.Maui.Media/
│  ├─ CarKit.Maui.Communication/
│  ├─ CarKit.Maui.Navigation/
│  └─ CarKit.Maui.Testing/
├─ tests/
│  ├─ CarKit.Maui.Core.Tests/
│  ├─ CarKit.Maui.Tests/          hosting and DI (sources of the modules' Hosting/, Renderers/, Media/, Communication/ and Navigation/ linked, net10.0)
│  ├─ CarKit.Maui.Build.Tests/    source generator and MSBuild targets
│  └─ CarKit.Maui.DeviceTests/
├─ samples/CarKit.Sample/        Parking, templates (Stages 2–4), category flows (Stage 7)

└─ docs/                           specification.md (this specification), release-checklist.md, manual-verification.md, site/ (documentation site in English; Stage 10)
```

**Conventions**

- Latest C#, `Nullable=enable`, `TreatWarningsAsErrors`, `Microsoft.CodeAnalysis.PublicApiAnalyzers`, `IsTrimmable` and `IsAotCompatible` set to `true`; zero reflection in rendering paths.
- Names: shared types `Car*`, platform types `CarPlay*` / `AndroidAuto*`, internal renderers `*Renderer` in `Platforms/`.
- Asynchrony: `ConfigureAwait(false)` in Core; no `async void` except native callbacks, which pass exceptions to `ICarErrorHandler` instead of crashing the process.
- Native object lifecycle: on disconnect, detach the `CP*` delegates and handlers and release references to `Screen` and `CarContext`, so the Java peer does not leak.
- Logging through `ILogger` with the `CarKit.*` category; the `LogNativeCalls` mode logs every platform call.
- One PR per stage or part of it. A public API change requires updating this specification in the same PR.

| Android Auto media templates (`MediaPlaybackTemplate`, Early Access) with no host to verify against | Template rejected by the host or no session token | Off by default (`CarKitAndroidTemplatedMedia`), renderer test on the emulator, a step in manual-verification |
| The Android Auto refresh and step rules for `ScreenManager.Remove` and `SectionedItemTemplate` are not documented | CarKit's step counter differs from the host's | The counter counts conservatively according to the `ListTemplate` rules; the host error "too many templates" to be verified in DHU |
| Messages and conversations verified without hosts (no DHU, CarPlay Simulator manual; Siri and the Intents Extension do not work on the simulator without an App Group and signing) | Reading/replying by voice in Android Auto, Siri in CarPlay and a CallKit call in the car behave differently from the tests | Native paths in device tests (a notification from `NotificationManager`, `PendingIntent` with `RemoteInput`, `ConversationItem` callback through the host delegate, extension handler on the store, `CXProvider` on the simulator); steps in manual-verification (Stage 6) |
| `ConversationCallback` through `java.lang.reflect.Proxy` (binding workaround) | R8 with obfuscation may rename the interface | Car App Library keeps the AIDL classes (`proguard.txt`); the CarKit.Maui package adds a `-keep` rule for the `ConversationCallback` interface |
